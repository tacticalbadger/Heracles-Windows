# Heracles for Windows, Stages 0 and 1: Repository, Skeleton and Spikes — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rebuild this repository around the native Windows app, get the Rust core building, bound to C# and tested on Windows behind an empty WPF window, and settle the four risks the later stages depend on.

**Architecture:** A new git history starts from the Mac repository's tree at 0.3.0 as the reference, then is cut down to the shared Rust core. A WPF app on .NET 10 loads the core through C# bindings generated by `uniffi-bindgen-cs`. PowerShell scripts adapted from the Toolbox Windows port build, test, package and drive it.

**Tech Stack:** Rust 1.100 (`heracles-core`, UniFFI 0.32, bundled SQLite), `uniffi-bindgen-cs` v0.12.0, .NET 10, WPF, C#, xunit, Windows PowerShell 5.1.

**Spec:** `docs/superpowers/specs/2026-11-22-native-windows-app-design.md`. This plan covers its stages 0 and 1. Stages 2 to 7 each get a plan of their own, written after this one lands, because what the spikes find changes them.

The spec lists six risks. Five are settled here (Tasks 6 to 10). The sixth, pictures WPF cannot decode, needs no spike: which formats decode depends on the codecs each PC has, so the behaviour is the same everywhere (try, catch, show a placeholder) and is pinned by a test in the editor-views plan.

## Global Constraints

- The Mac repository is the clone at `..\Heracles`. Its reference commit is `5dd0252` (tree `7a3e5b1dc51b4efae8f8f5ccb76ec3870d1f0681`). Read it; never add it as a remote here and never push to it.
- The Toolbox Windows port is the clone at `..\Toolbox_Windows`. Scripts and project files are adapted from it. Read it; change nothing there.
- Work happens on the branch `port`. The old `main` stays untouched locally and on GitHub. **Nothing is pushed.** Replacing `main` on GitHub is Task 11 and needs the owner's word at that moment.
- Commit author for every commit: name `tacticalbadger`, email as on the Mac repository's commit `5dd0252`. Set in this repository's own config (Task 1).
- Commit messages end with: `Co-Authored-By: Claude Fable 5.2 <noreply@anthropic.com>`
- Nothing of the owner's own setup goes in git: no real names, account emails, hostnames, employer, or paths under the profile folder. Write "the owner". Use `corp.example`, `jdoe`, `ACME` where an example is needed.
- Scripts are Windows PowerShell 5.1: no `&&`, ASCII only, CRLF. Everything else is LF.
- Start the build scripts from PowerShell, not Git Bash. Use absolute paths in commands.
- App: `net10.0-windows10.0.22621.0`, `SupportedOSPlatformVersion` `10.0.19041.0`, runtime identifiers `win-arm64;win-x64`. No Windows Forms, no WebView2.
- C# bindings: namespace `Heracles.Core`, free functions in class `CoreApi`, native library `heracles_core.dll`.
- Version file `VERSION` holds `0.2.0`. The build number is the commit count.
- Environment overrides: `HERACLES_DATA_DIR` (library folder) and `HERACLES_LOG_PATH` (log file). Without them: `%APPDATA%\Heracles` and `%LOCALAPPDATA%\Heracles\heracles.log`.
- Never run the app on the owner's real library in a test. Launch through `tools\e2e\launch.ps1`, which sets both overrides.
- Never stop every `Heracles` process: filter by the build's path.
- The owner may be at the PC. Prefer UI Automation patterns (`invoke`, `setvalue`, `select`) to real clicks and keys. Do not write to the clipboard.
- Spike code is throwaway. It lives under `build\spikes\` (ignored by git) and is never committed. What a spike found goes into `CLAUDE.md`.

## Review Focus

Inputs and conditions the spec implies that are most likely to bite, each pinned by a test in the task that owns the code:

1. **The library folder cannot be used** (a file is in the way, or it cannot be written). Expected: the window says the library could not be opened and why; no crash. Task 4.
2. **The library folder's path has spaces and non-ASCII letters**, as profile folders do. Expected: the library opens. Task 4.
3. **A `file://` picture URL that is not the simple case**: a drive letter, a lowercase drive, `localhost`, percent-encoding, or a host that is another machine. Expected: local ones resolve; another machine's is left as written, never read as a relative path. Task 3.
4. **The change feed arrives on a thread that is not the caller's.** Expected: the C# observer is called, on that thread, with the right batch. Task 4.
5. **The build is started from an emulated x64 shell on the ARM64 machine.** Expected: the ARM64 library lands in the ARM64 slot, or the build stops with a message; never an ARM64 library in the x64 slot. Task 4.

- [ ] **Step 3: Implement `file_url_path` and use it**

`fn file_url_path(rest: &str) -> Option<PathBuf>`, where `rest` is the URL after `file:`. Rules: if `rest` starts with `//`, the text up to the next `/` is the host; an empty host or `localhost` (any case) is this machine, any other host returns `None`. What follows is the path, percent-decoded with the existing `decoded`. On Windows only (`cfg!(windows)`), a path that begins `/`, an ASCII letter, `:` loses its leading `/`. In `local_image_file`, the `Some("file")` arm becomes `file_url_path(&src[5..])?`.
